Elastic Beanstalk, end to end

What it actually does under the hood, what it costs (spoiler: the service itself is free — your EC2 isn't), and a full interview drill covering architecture, deployment policies, and the "why not just use X" questions that trip people up.

§01

What Elastic Beanstalk is

Elastic Beanstalk (EB) is AWS's application orchestration layer: you hand it a zip of your code, and it provisions and wires together the EC2 instances, Auto Scaling group, load balancer, security groups, and CloudWatch alarms needed to run it — then keeps managing that infrastructure as you ship new versions.

It isn't a new compute primitive. Under the hood an EB "environment" is ordinary EC2, an ordinary Application Load Balancer, and an ordinary Auto Scaling group, all provisioned via CloudFormation on your behalf. What EB adds is the opinionated glue: a standard way to package a release, a health-reporting agent on every instance, a rotation of deployment strategies, and a CLI/console that turns a dozen manual console clicks into eb create.

YOU PROVIDE

Application code

A source bundle (zip) or Docker image, plus optional config in .ebextensions/ or .platform/.

EB PROVIDES

Running infrastructure

EC2 + ASG + ALB + security groups + CloudWatch alarms + an S3 bucket holding every app version you've deployed.

YOU RETAIN

Full control

Every resource EB creates is visible and editable in its own console — nothing is hidden or locked away.

§02

How it works, step by step

Two vocabularies get you through almost every EB workflow: the console path (click-driven, good for first launches) and the EB CLI path (eb command, good for repeatable deploys). Both do the same five things underneath.

  1. Create an application — a logical container/namespace for your project (e.g. student-score-predictor).
  2. Upload a version — EB zips your source, stores it in an EB-managed S3 bucket, and labels it a numbered/tagged application version.
  3. Launch an environment — you pick a platform (Python 3.12, Node 20, Docker, …) and a tier (Web Server or Worker); EB runs a CloudFormation stack that stands up EC2, ASG, ALB, and security groups.
  4. Deploy — EB pushes the chosen application version onto the environment's instances using whichever deployment policy you've configured (§04).
  5. Manage — EB continuously polls an on-instance health agent and CloudWatch metrics, feeding the environment's traffic-light health status and driving Auto Scaling.

Architecture & core concepts

Three nouns cover the object model: Application → Application Version → Environment. An application can have many versions (your deploy history) and many environments (e.g. staging, prod) — any version can run in any environment.

Web server tier

Standard request/response environment sitting behind an ALB. This is what nearly every EB app uses — a Flask, Django, Express, or Spring app answering HTTP.

Worker tier

No load balancer. Instances poll an EB-managed SQS queue and run a background daemon — built for async jobs (email sends, report generation, model batch scoring).

Saved configuration

A snapshot of an environment's settings (instance type, scaling limits, env vars) you can save, version-control, and reapply to spin up an identical environment elsewhere.

.ebextensions / .platform

.ebextensions/*.config (YAML) customizes option settings, packages, and commands. Newer .platform/hooks/ scripts give you pre/post-deploy shell hooks.

§04

Deployment policies

The deployment policy is the one setting most likely to come up as a scenario question, because it's a genuine engineering trade-off between downtime, cost, and rollback safety — not a solved problem with one right answer.

Choosing a deployment policy
PolicyDowntimeExtra costRollbackUse when
All at onceYesNoneManual redeployDev/test environments where a blip is fine.
RollingReduced capacityNoneSlow (roll forward again)Prod, cost-sensitive, can tolerate brief reduced capacity.
Rolling + additional batchNone1 extra batch, temporarilySlowSame as rolling, but capacity must never dip.
ImmutableNoneFull new ASG, briefly (2×)Fast — just terminate new ASGProd deploys where a bad build must never touch live traffic.
Traffic splittingNoneFull new ASG, brieflyInstant — shift % backCanary-testing a risky release against a slice of real traffic.
Blue/green manualNoneSecond full environmentInstant — swap backMajor version jumps, schema changes, "I want a full dress rehearsal."
Mechanism note

Immutable and traffic-splitting both launch an entirely new Auto Scaling group alongside the old one and health-check it before it takes real traffic — that's what makes them safe. The difference is immutable cuts over 100% at once after checks pass; traffic-splitting ramps a configurable percentage over an evaluation window first. Blue/green isn't a policy EB applies automatically — it's a pattern you execute yourself by standing up a second environment and running eb swap to exchange CNAMEs once you're satisfied.

§05

Pricing & the free tier

The one-line answer

Elastic Beanstalk itself carries no additional charge — AWS doesn't bill for the orchestration layer. You pay only for the underlying resources it creates on your behalf: EC2 instance-hours, the Application Load Balancer, S3 storage for versions/logs, CloudWatch alarms, and (if you add one) RDS.

That makes "is Elastic Beanstalk free?" a bit of a trick question in an interview — the correct answer distinguishes the service (free) from the infrastructure it provisions (billed normally, same as if you'd built it by hand).

Worth knowing in 2026

AWS accounts created before July 15, 2025 keep the classic 12-months-free structure above. Accounts created after that date follow AWS's newer free-tier model — a bundle of "Always Free" services plus a time-limited credit balance — so the exact free EC2/ELB hours a brand-new account gets may differ. Always check the Billing → Free Tier page for the account in question rather than quoting a fixed number.

Illustrative on-demand costs beyond the free tier (us-east-1, subject to change — never quote these as current fact without checking the AWS Pricing page):

  • t3.micro Linux EC2 ≈ $0.0104–0.0116/hr
  • Application Load Balancer ≈ $0.0225/hr + per-LCU processing charge
  • S3 Standard storage ≈ $0.023/GB-month

Two cost traps that are common interview "gotchas": Immutable and traffic-splitting deploys briefly double your instance count (a second ASG runs alongside the first), and a multi-AZ, load-balanced environment is EB's default recommended shape for prod — appropriate for real traffic, but overkill (and non-free) for a personal project, where a single-instance, no-load-balancer environment is cheaper and still fully supported.

§06

EB vs. the rest of the AWS compute fleet

The recurring interview pattern is "why would you use EB instead of X" — the honest answer is always about where you want to spend engineering effort: infrastructure control vs. shipping speed.

Where Elastic Beanstalk sits among AWS compute options
ServiceModelOps burdenBest fit
Elastic BeanstalkPaaS over EC2LowStandard web apps/APIs you want deployed fast with room to customize later.
EC2 (raw)IaaSHighFull control — custom networking, non-standard runtimes, fine-grained tuning.
LightsailSimplified VPSLowSmall sites/blogs, flat predictable pricing, minimal AWS knowledge needed.
ECS / FargateContainer orchestrationMediumMicroservices, teams already containerizing, need for fine scheduling control.
Lambda / App RunnerServerlessVery lowEvent-driven or bursty workloads; App Runner specifically for containerized web services with true scale-to-zero.

A useful framing to say out loud in an interview: EB automates infrastructure you still own (you can see and edit every EC2/ALB/ASG resource it made); Lambda/App Runner abstract the infrastructure away entirely (there's no server to look at); ECS/Fargate sits in between, giving you container-level control without EC2 management (on Fargate) or with it (on EC2 launch type).

§07

Pros, cons, and when to skip it

STRENGTHS

Fast path from code to a load-balanced, auto-scaled, HTTPS-capable URL. Zero lock-in — every resource is standard EC2/ALB/ASG you can reach directly. Built-in deployment strategies remove a lot of hand-rolled rollout scripting. Free to use; you're only ever paying standard resource rates.

LIMITATIONS

Coarser-grained than hand-built infra — some networking/scaling edge cases need .ebextensions workarounds rather than a console toggle. Not a natural fit for many independently-scaled microservices (that's ECS/EKS territory). Environment updates can be slower than a container redeploy. Config drift is possible if someone edits provisioned resources directly instead of through EB.

Rule of thumb: reach for EB when the shape of your app is "a web service (or worker) that needs to scale," and you'd rather not hand-assemble the ALB/ASG/CloudWatch wiring yourself. Reach past it — to ECS/EKS for many small services, or Lambda for spiky/event-driven work — once your architecture stops looking like "one app, scaled out."

§08

Worked example: deploying this repo's Flask app

This project already has the shape EB expects for a Python web-server tier: a Flask app (app/app1.py) with a requirements.txt. Here's the concrete path from local code to a public EB URL.

  1. Give EB an entry point. The modern Python platform looks for a WSGI callable; simplest is a top-level application.py that does from app.app1 import app as application, or point the platform at app.app1:app via a Procfile.
  2. Add a Procfile (recommended over relying on default detection):
Procfile
web: gunicorn --bind :8000 --workers 3 app.app1:app

(add gunicorn to requirements.txt — the Flask dev server in app.run() shouldn't serve production traffic.)

  1. Initialize EB from the project root:
eb init -p python-3.12 student-score-predictor --region ap-south-1
eb create student-score-predictor-env --single

--single skips the load balancer/multi-AZ setup for a single free-tier-eligible instance — appropriate for a portfolio/demo deployment; drop it for a prod-shaped environment with an ALB and Auto Scaling.

  1. Ship the trained model artifact. Either commit small artifacts/model.pkl/preprocessor.pkl files into the deploy bundle, or set an .ebextensions env var pointing at an S3 location and fetch it in a .platform/hooks/predeploy script — cleaner once the model grows past a few MB.
  2. Deploy and iterate:
eb deploy
eb open      # opens the live URL in a browser
eb logs      # tail instance logs if predict_pipeline errors out

From here, switching the environment's deployment policy to immutable (§04) before adding real users is the natural next step — it costs one extra instance-hour per deploy and buys a much safer release process than the default rolling policy.

Fundamentals

What is AWS Elastic Beanstalk?

A PaaS orchestration service: you upload application code and EB provisions, deploys to, and manages the EC2/ALB/Auto Scaling/CloudWatch infrastructure needed to run it, while leaving every resource it creates directly accessible to you.

Is Elastic Beanstalk PaaS or IaaS?

PaaS by behavior — you don't provision servers yourself — but it's built entirely on IaaS primitives (EC2, ALB, ASG) that remain visible and editable, which is why some call it "PaaS with an IaaS escape hatch."

How does EB differ from CloudFormation?

CloudFormation is a general infrastructure-as-code engine — you author the full resource graph yourself. EB is opinionated and application-focused: it generates and manages a CloudFormation stack for you based on a platform choice and a code bundle, trading flexibility for speed. In fact, EB environments are CloudFormation stacks under the hood.

How does EB differ from OpsWorks?

OpsWorks is a Chef/Puppet-based configuration-management service for orchestrating custom server layers and lifecycle events — more control, more setup. EB trades that flexibility for a much faster, more opinionated "upload and go" workflow aimed at standard web apps.

What languages/platforms does Elastic Beanstalk support?

Java, .NET/.NET Core, PHP, Node.js, Python, Ruby, Go, and Docker (single- or multi-container), running on servers like Apache, Nginx, Passenger, and IIS depending on platform.

Do you lose control of the infrastructure by using EB?

No — every EC2 instance, load balancer, security group, and Auto Scaling group EB creates is a normal resource in your account, visible in its own console and editable directly if needed (though direct edits can drift from what EB expects, so config changes are best made through EB's saved configuration or .ebextensions).

Architecture & components

What is an EB Application?

The top-level logical container for a project — it groups together application versions and the environments that run them.

What is an Application Version?

A specific, immutable deployable build of your code, stored as a labeled bundle in an EB-managed S3 bucket. Any version can be deployed to any environment under the same application.

What is an Environment?

A running collection of AWS resources (EC2/ASG, optionally ALB) executing one application version, configured by a specific platform and configuration set — e.g. a staging and a prod environment for the same application.

What's the difference between Web Server tier and Worker tier?

Web Server tier serves HTTP requests behind an Application Load Balancer. Worker tier has no load balancer; instances instead poll an EB-managed SQS queue and process messages via a daemon — built for asynchronous background jobs.

What is a saved configuration / configuration template?

A reusable snapshot of an environment's settings (instance type, scaling bounds, environment variables, etc.) that can be applied when creating new environments, so staging and prod can be kept consistent.

What is .ebextensions used for?

A folder of YAML/JSON config files deployed alongside your app that let you set option settings, install OS packages, run commands, and create files/resources during environment provisioning — the primary way to customize EB beyond the console.

What AWS resources does a default Web Server environment create?

An Auto Scaling group of EC2 instances, an Application (or Classic) Load Balancer, security groups, an S3 bucket for versions/logs, and a set of CloudWatch alarms driving scaling and health.

Deployment & scaling

What deployment policies does EB support?

All at once, Rolling, Rolling with additional batch, Immutable, and Traffic Splitting — plus the manual Blue/Green pattern via environment swap. See the comparison table in §04.

Explain Rolling vs. Rolling with additional batch.

Rolling updates instances in batches, taking each batch out of service during its update — so total capacity briefly dips. Rolling with additional batch first launches one extra batch of new instances, keeping full capacity throughout, at the cost of running slightly more instances temporarily.

Why are Immutable deployments considered safer?

They launch a complete second Auto Scaling group running the new version, health-check it fully before routing any production traffic to it, and simply terminate it if checks fail — the original instances are never touched, so a bad build can't take down the live environment.

What is a Traffic Splitting deployment?

A canary-style policy: EB stands up a new instance set (like Immutable), then routes a configurable percentage of live traffic to it for an evaluation window. If health checks fail, or you abort, traffic shifts back and the new instances are torn down — with zero downtime either way.

How does Blue/Green deployment work in EB?

You deploy the new version to a completely separate environment (not the live one), test it independently, then run eb swap to exchange the two environments' CNAMEs — instantly cutting traffic over. Rolling back is just swapping back.

How does Auto Scaling work in an EB environment?

EB configures a standard Auto Scaling group with CloudWatch-alarm-driven scaling policies (commonly CPU utilization, but configurable to other metrics), plus min/max instance bounds you set in the environment configuration.

How does EB's health monitoring work?

Basic health reporting uses ELB/EC2 status checks. Enhanced health reporting (default on newer platforms) runs an agent on each instance that reports application-level metrics (response time, request counts, process status) feeding a color-coded status: OK, Info, Warning, Degraded, Severe.

What happens if a deployment fails health checks?

Depends on policy: Immutable/Traffic-Splitting automatically terminate the unhealthy new instances and leave the old version serving traffic untouched. Rolling policies can be configured to roll back automatically on a set number of failures, otherwise the environment surfaces a Degraded/Severe health status for manual intervention.

Operations & troubleshooting

How do you view logs from an EB environment?

eb logs pulls the latest rotated logs (or a full bundle with --all); for continuous visibility you enable log streaming to CloudWatch Logs from the environment configuration.

Can you SSH into EB instances?

Yes — eb ssh connects to an instance directly, provided a key pair was associated at environment creation (or added afterward). Useful for reading local logs or debugging a stuck deploy hook.

How do you roll back a bad deployment?

Re-deploy a previous, known-good Application Version from the environment's version history (console "Application versions" or eb deploy --version) — EB doesn't auto-keep a "previous" pointer beyond that version history.

How do you monitor an EB environment in production?

Through EB's built-in health dashboard for a quick signal, backed by CloudWatch metrics/alarms and CloudWatch Logs (or a shipped-out log pipeline) for deeper investigation, same as any EC2/ALB workload.

How do you manage environment variables and secrets?

Simple config lives in the environment's "Software" configuration or under .ebextensions' aws:elasticbeanstalk:application:environment namespace. Real secrets shouldn't live in either — fetch them at boot from Secrets Manager or SSM Parameter Store via a .platform hook instead.

What's the difference between the EB Console and the EB CLI?

The console is click-driven and best for exploring options or one-off setup; the CLI (eb) is scriptable and reproducible, making it the better fit for CI/CD and repeatable local workflows — both operate on the same underlying environments.

Security

What IAM roles does EB use?

Two distinct roles: a service role that EB itself assumes to call other AWS APIs on your behalf (provisioning resources, monitoring), and an instance profile attached to the EC2 instances so your running application can call AWS APIs (e.g. reading from S3).

How do you enable HTTPS on an EB environment?

Attach an ACM certificate to the environment's load balancer listener (HTTPS on 443) via the console or .ebextensions; typically paired with an HTTP→HTTPS redirect rule on the ALB.

Can EB run inside a custom VPC / private subnets?

Yes — you can place instances in private subnets with the load balancer in public subnets (a standard pattern), configured via the environment's VPC settings at creation or in a saved configuration.

How do you restrict access to an EB environment?

Security groups on the ALB/instances for network-level restriction, IAM policies to control who can manage the environment itself, and — for non-public apps — putting the ALB fully in private subnets or behind a VPN/bastion.

Cost & pricing

Is Elastic Beanstalk free?

The EB service itself has no additional charge. You pay standard rates for whatever EC2/ALB/S3/RDS resources it provisions — the same as if you'd built the environment by hand. See §05.

What drives the cost of running an app on EB?

Mainly EC2 instance-hours and instance type, whether a load balancer is attached, data transfer, S3 storage for versions/logs, and any attached RDS database — plus a temporary doubling of instance count during Immutable/Traffic-Splitting deploys.

How would you minimize EB costs for a low-traffic app?

Use a single-instance environment without a load balancer (eb create --single) for non-critical/demo workloads, stay within a free-tier-eligible instance size, set tight Auto Scaling max bounds, and prefer Rolling over Immutable deploys if the extra-instance cost during releases matters.

Scenario & behavioral

"Our last deploy caused a few minutes of user-facing downtime — how do you prevent that?"

Identify what policy was in use — All at once or a too-aggressive Rolling batch size are the usual culprits — and move to Immutable or Traffic Splitting so the new version is fully health-checked before it ever receives production traffic.

"Users see intermittent 502s right after a scale-out event — how do you debug it?"

Check whether new instances are being marked healthy by the ALB before traffic hits them (connection draining / health check grace period), inspect eb logs for app startup errors on the new instances, and confirm the ALB health-check path actually reflects app readiness rather than just process liveness.

"We need zero-downtime deploys with an instant rollback path — what do you pick?"

Immutable for zero-downtime with an automatic safety net (bad builds never reach production instances), or Traffic Splitting if you also want to canary-test against a slice of real traffic before full cutover — both allow near-instant rollback since the old instance set is untouched until cutover completes.

"How would you wire EB into a CI/CD pipeline?"

A pipeline (CodePipeline, GitHub Actions, Jenkins) builds/tests the app, then invokes the EB CLI or the CreateApplicationVersion/UpdateEnvironment APIs to push a new version to a target environment — typically staging first, then promoted to prod via environment swap or a second deploy step after manual/automated approval.

Comparison questions

"EB vs. raw EC2 — when would you choose each?"

EB when you want a standard app deployed and scaled quickly without hand-building the ALB/ASG/CloudWatch wiring. Raw EC2 when you need infrastructure that doesn't fit EB's model — unusual networking, non-standard runtimes, or very fine-grained tuning EB's abstractions get in the way of.

"EB vs. ECS/Fargate — when would you choose each?"

EB suits a single app (or a small number of them) that scales as one unit. ECS/Fargate fits systems decomposed into several independently-deployed, independently-scaled microservices, where container-level scheduling and service discovery matter more than a fast single-app path.

"EB vs. Lambda / App Runner — when would you choose each?"

Lambda/App Runner for event-driven or spiky workloads that benefit from true scale-to-zero and no server management at all. EB for workloads that run continuously and benefit from being "always warm," or that need OS-level access/long-running processes Lambda's execution model doesn't fit well.

"EB vs. Lightsail — when would you choose each?"

Lightsail for small sites/simple apps where flat, predictable pricing and minimal AWS knowledge matter more than scaling sophistication. EB once you need real Auto Scaling, multiple environments (staging/prod), and deployment-policy control that Lightsail doesn't offer.
